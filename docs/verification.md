## Build and runtime bridge contract

`src-tauri/build.rs` invokes `swiftc` whenever the Swift source changes and writes the bridge to Cargo's active profile directory. It also creates Tauri's target-triple sidecar input. Rust resolves the bridge relative to the running Rust executable rather than using a source-tree path. Tauri bundles it beside the app executable, so relocating the `.app` does not break that lookup.

## Communication evidence

Observed directly:

- Rust's focused test executed the built Swift process and validated its typed response.
- A clean Tauri bundle contained the bridge beside the Rust executable.
- The relocated bridge returned real status JSON.
- The relocated Tauri process launched and owned an on-screen native window.
- The real bundled WebView invoked `native_status`, received the Rust command response and the typed `runtime-status` event carrying the same nonce/timestamp, then invoked `acknowledge_frontend`. Rust validated both receipts and wrote the structured local marker below to `docs/native-handshake.log`:

```text
INTERVJUARE_NATIVE_HANDSHAKE {"status":"verified","nonce":"83592-1791366074357","timestampMs":1791366074357}
```

The acknowledgement command rejects a missing or mismatched pending nonce/timestamp. A pending handshake that is not acknowledged within eight seconds produces a structured `timeout` marker. Verification is local stderr only; no telemetry or sensitive interview data is emitted. Visual rendering was not captured because Computer Use was unavailable, but frontend execution and both IPC receipt paths are proven by the Rust-issued nonce that only the bundled WebView receives and returns.
